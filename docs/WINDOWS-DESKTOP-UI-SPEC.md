# Windows 桌面端界面规格 v3.4（单页 + 日历 + 卡片栅格 + 缩略图直操 + 快捷键，日历除外）

> 适用模块：`desktop/ui`、`desktop/core`（`copyPhotos` 为本次新增）
> 依据：`desktop/core` 的 `PhotoMgmCore` 接口与其 447 个测试所固定的行为语义
> 状态：已实现。本文是实现与设计意图的对照说明，不是待做的设计稿
> 历史：v1.0（U1 三栏骨架）→ v2.0（四阶段切换）→ v3.0（单页 + 弹窗）→ v3.1（日历 / 卡片栅格）→ v3.2（红框 / 弹窗瘦身 / 搜索与复制）→ v3.3（恢复快捷键；日历仍不吃键盘）→ v3.4（主页面缩略图直接移动/复制 + 结果通知）。前四版均已删除

---

## 0. 这一版为什么又改

v2.0 把界面切成 `INPUT / REVIEW / EXPORT / RESULT` 四个互斥页面，理由是"业务流程有四步"。这个映射错在把**数据阶段**当成了**人的工作单元**：

| v2.0 的假设 | 实际发生的事 |
| --- | --- |
| 输入是"第一步"，做完就离开 | 输入只在当天开工时做一次，之后整天都在看事件 |
| 复核和导出是两个页面 | 导出的判断依赖事件列表；导出后还要回列表补照片 |
| 结果是一个页面 | 结果只需要三四行字，却占掉整屏，用户第一反应是"关掉回去" |
| 日志框是"编辑器"，要能看全文能改 | 日志是外部产出的文本，粘进来就完事；常驻一个 96 dp 的框把事件挤到只剩两行 |

v3.0 的约束（用户明确提出）：

1. **除设置外，所有按钮在同一页**；
2. **日志输入框只负责"输入"，尺寸精简，解析后自动隐藏**；
3. **同一页面能看到所有事件及其照片**；
4. **点事件弹出窗口，在窗口里对照片操作**。

这四条不是排版口味，正好对应三件事实：日志是一次性输入、事件是常驻工作对象、照片操作的上下文是"某一个事件"。下面的结构全部由此推导。

**v3.1 又改了三处**（都是"结构合理 / 层级清晰 / 统一"的具体化，不是换皮）：

| 改动 | 原来 | 现在与理由 |
| --- | --- | --- |
| 巡查日期 | 手输文本框 `2026-11-01` + 前后一天 | **日历面板**。手输的错法是"静默无效"（`2026-13-01` 被吞掉，用户以为改成功），且看不到"这个月哪几天在干活"（§6.3） |
| 事件列表 | 卡片，但列宽靠内容自适应 | **卡片 + 固定栅格**：序号 26 / 时间 96 / 张数 56 / 头部 30，同一字段上下对齐（§2.2、§7.1） |
| 区块层级 | 工具条与列表同底色相接 | 工具条下方加 1 dp 分隔线；空状态改为限宽 520 居中 + 提示条（§2.1） |

**v3.3 的一条修正**：v3.2 把"移除所有键盘操作"当成了全局要求，实际用户只要求**日历**不做键盘操作。本轮把 `AppShell` 的快捷键整套复原（`Ctrl`+点多选也一并回来），只保留日历的"不吃键盘"（§6.2）。下表是 v3.2 的六条，第一条已按 v3.3 修正。

## 1. 运行逻辑（不变的部分）

### 1.1 一条流水线，两个原子动作

```
巡查日期 + 源目录 + 日志原文 ──analyze()──> 台账（事件 + 未匹配池） ──export()──> 产物
                                    ↑                                  │
                                    └── 人工调整（移动/指定台账格/重置）──┘
                                        不重新分析，立即生效
```

- `analyze()` 是**原子**的 7 步：解析日志 → 扫目录 → 文件名日期粗筛 → 内容哈希去重 → EXIF 批读 → GPS 聚类 → 分类。界面上不能拆成两个按钮。
- 人工调整只有三个动作：`movePhotos`、`markLedgerPhoto`、`resetManualAdjustments`，全在内存模型上做。
- `export()` 写副本，取消保留已复制文件，下次按 manifest 续传。

### 1.2 数据形状决定了界面形状

- `EventSnapshot.photoIds` —— **照片是事件的字段**。所以"事件 + 它的照片"应该在同一张卡片里，而不是左右两栏。
- `state.events` 是**日志顺序**；`state.ledger` 是 `endTimeMs` 顺序。两者下标不对应，必须按 `(location, description)` 顺序消费配对（`model/LedgerJoin.kt`）。
- `unmatchedPhotoIds` 是必须交付的东西（进 `99_未分类/`），所以它在列表里占一个固定位置，不是"垃圾桶"。

### 1.3 状态机只有 6 个值，且没有 EXPORTED

`IDLE / ANALYZING / READY / EXPORTING / FAILED / CLOSED`。导出成功后回到 `READY`，结果在 `state.lastExport` 里 —— 所以"导出完成"必须由界面用 `lastExport.exportDir` 的**边沿变化**识别，不能等状态。

## 2. 由逻辑 + 约束推出的结构

### 2.1 一层页面，四层覆盖

```
顶栏        我在处理哪一天 / 能不能导出 / 设置
消息条      出什么事了（错误不自动消失）
──────────────────────────────────────────────
日志条      未解析=72 dp 输入区；已解析=一行摘要（36 dp）
结果条      上次导出成功了吗（仅导出后出现，可收起）
工具条      看哪一批事件（筛选/搜索/去重口径）
事件卡片    一屏 3~5 张：标题行 + 照片行
──────────────────────────────────────────────
状态栏      口径与快捷键
```

覆盖层（同一时刻最多一个）：**设置 / 某事件的照片 / 移动到某事件 / 重新分析确认**。

### 2.2 事件列表用卡片，但卡片内部是固定栅格

- 依据：`photoIds` 是事件字段；复核的动作是"看这一条对不对"，一次只看一个事件。
- 结论：一张卡片 = 一个事件（= 台账一行 = 导出一个文件夹）。标题行给序号、时间、桩号、描述、问题标签、张数；照片行给缩略格。
- 取舍：卡片里放不下就**少放几格 + 末位「+N」**，不给横向滚动条。一旦能横滑，用户就看不到"这个事件到底几张"，而"几张"正是要判断的东西。

**为什么不是表格（三个候选都评估过）**

| 形态 | 好处 | 在本场景的致命点 |
| --- | --- | --- |
| 表格（每事件一行） | 列对齐最好，可排序 | 照片是"一组且数量可变（0~5）"，行高被撑成锯齿；行内塞缩略图后和卡片长得一样 |
| 纯列表（一行文字） | 最密 | 看不到照片，复核时必须逐条点开，8 个事件点 8 次 |
| 卡片（本版） | 一个事件一个单元，文字与照片同框 | 对齐靠人工栅格，否则每张卡片各排各的 |

**所以卡片内部按表格做**：序号列 26、时间列 96、张数列 56，三列固定宽；头部行高 30；照片条与序号列同一左边缘。这样既有"一个事件一个单元"，又有"同一字段上下对齐"。

高度**不强行相等**：无照片时用 40 dp 的占位行（与照片条同左边缘、同圆角），比有照片的卡片矮。540 dp 高的内业机上一屏能多看半张卡片，比"两列高度完全一致"更值。

### 2.3 照片操作放进弹窗，因为操作的上下文就是"这个事件"

- 依据：移动照片必须看到"候选全貌"和"当前这张"；而列表里两者都摆不下。
- 结论：点卡片 → 覆盖层（标题 + 左大图 + 右侧事实 + 底部缩略条 + 操作条）。
- 弹窗里能做的：切照片、Ctrl 多选、移到其他事件、移出到未匹配、指定台账第 1/2 格、恢复自动、打开原文件、上一/下一事件。

### 2.4 弹窗用**窗口内覆盖层**，不用独立窗口

不是审美问题：`androidx.compose.ui.window.Dialog` 在 125% 缩放的机器上是独立 OS 窗口，会被系统按另一套 DPI 处理 —— 实测显式给 830×455 dp 渲染成了约 440×455，标题被裁、操作条按钮溢出到窗口外。改为 scrim + 卡片后，尺寸与主窗口同一套度量，焦点与截图行为都可预期。

**可拖动（v3.5）**：遮罩是整窗的，弹窗永远居中就意味着**永远挡住同一块区域**。现在头部是拖动手柄（悬停显示"移动"光标），位移被夹在窗口内（四边各留 8 dp），不会拖出可视区找不回来。拖动识别要求"按下后位移超过 `touchSlop`"，所以头部里的 `✕` / `‹` `›` 照常可点 —— 这一点是**必需**的，否则为了能拖动会把关闭按钮做成点不动。

### 2.5 日志框只做"入口"，解析后自动收成一行；日期与它同处一带

- 依据：日志是外部产出，粘贴即完；`setLogText` 自带防抖落盘，不需要"保存"。
- 结论：默认展开一块 72 dp 的粘贴区 + 一个主按钮「开始分析」；`analyze()` 完成后自动收成一行摘要（`事件 N · 照片 M · 未匹配 K · 巡查人`），右侧留「重新分析」「重新输入」。
- 例外：**解析出 0 个事件时日志框保持展开**，否则用户连改的地方都没有（已单测）。
- 日志原文不会丢：core 持久化，点「重新输入」原样回来。
- **巡查日期在这一带的左侧、两种形态下都常驻**（v3.2 从设置里搬出来）：日期和日志是 `analyze()` 的两个输入，改日期 → 重新分析必须是一条不断开的动作链；日期又是"项目主键"，任何时候都要看得见。代价是常驻一条 312 dp 的日期列，换来"我在处理哪一天"永远不用猜。
- 改完日期后，若已有结果，弹一条可关闭的提示说清"下一步点重新分析"，而不是把人拦在确认框前（改日期只是输入，不销毁任何东西）。

### 2.6 导出是顶栏一个按钮，结果是一条可收起的横幅

- 依据：导出前置条件只有"输出目录 + READY + 有事件"，全在 `state.canExport` / `WorkQueue.exportBlockers` 里。
- 结论：顶栏「导出」直接开始；缺条件时按钮禁用，状态栏与状态胶囊说明原因；导出中显示覆盖层（可取消，取消语义按分析/导出分别说明）；完成后顶部出现结果条：统计 + 打开目录 + 打开台账 + 收起。
- 结果条不占独立页面：用户接下来的动作是"回列表补照片"或"打开目录交付"，两者都要看着列表。

### 2.7 设置是唯一弹窗化的"非照片"入口

里面只放三类东西：分析输入（源目录）、导出输出（目录、是否生成台账、续传校验）、一个明确回退（恢复最初分类）。
去重口径**不在这里**——它是视图参数（core 同步重算、不重扫），放列表工具条上才符合"边看边切"。
巡查日期**也不在这里**（v3.2 起）：它是分析输入，但每次开工都可能改，藏在弹窗里等于多两次点击（§2.5）。

### 2.8 照片的三种归属操作：移动 / 复制 / 移出

| 动作 | 语义 | 界面入口 | core |
| --- | --- | --- | --- |
| 移动 | 它属于那边（原事件不再有） | 照片层「移动到…」→ 选目标事件 | `movePhotos(ids, eventId)` |
| 复制 | 两个事件都要用它（原事件保留） | 照片层「复制到…」→ 选目标事件 | `copyPhotos(ids, eventId)`（本次新增） |
| 移出 | 它不属于任何事件 | 照片层「移出到未匹配」 | `movePhotos(ids, null)` |

**两个入口，同一条路径**：照片层（弹窗内多选后）与**主页面缩略图的悬停层**（§6.6）都只是"选出对象"，
确认与校验都在同一个目标选择层里完成 —— 两条路径的行为、文案、错误处理完全一致，不需要维护两份。
两个入口的分工是：主页面用来"扫视时就手改对的那一两张"，照片层用来"进入某个事件后整理一批"。

复制是唯一会让"一张照片出现在两个事件里"的操作，因此：
- 卡片与缩略图上不额外打标（照片本身没变），**但侧栏会列出「本次归属（N 处）」并允许「移除本份」**；
- 状态栏的「已归属」按**去重后的照片张数**统计，不是事件照片格之和，否则会出现"已归属 13 / 共 12 张"；
- 移动会**清掉这张照片的复制关系**（移动表达的是"归属变更"，保留旧复制份会让用户看到"移走了却还在原来那条里"）。

三者**都在同一处目标选择层里完成确认**：候选列表排除照片当前所在的事件（不能移到它已经在的地方），
复制模式还会隐藏"已经持有全部所选照片"的目标（`Feedback.rejectReason` 是这套校验的唯一出处，
与界面无关，见 §6.6）。

## 6. 交互

### 6.1 选择模型（一次点击只做一件事）

| 动作 | 结果 | 锚点 |
| --- | --- | --- |
| 点缩略图本体（红勾区以外） | 设为当前预览（左大图），并把勾选**重置为只有这张** | 移到这张 |
| `Shift` + 点缩略图本体 | 从**锚点**连选到这张（连续一段，替换原勾选），同时设为当前 | **不动** |
| 点缩略图右上角红勾（24 dp 命中区） | **唯一**的"把这张加入/移出待操作、保留其它勾选"入口；**不改预览** | 移到这张 |
| 不勾选就按动作按钮 | 作用对象 = 当前那张（`operationTargets`：勾了用勾的，没勾用当前的） | — |
| 关闭弹窗 | 勾选集合与锚点一起清空（跨事件移动无意义） | 清空 |

**区域判定必须是几何，不能靠"子节点消费了没"猜（v3.7 修的真事故）**：旧实现是 `event.changes.none { it.isConsumed }`，指望右上角红勾的 `clickable` 先把 press 消费掉。但 `clickable` 只在**抬起**时才确定这是一次 tap，按下阶段并不保证消费，而 Main pass 是子先父后 —— 于是"点红勾"经常同时跑 `onToggle`（切换）和 `onActivate`（重置为一张），后者把前者覆盖，看起来就是"红勾没用 / 选不中第三张 / 连点几下勾选自己乱跳"。
现在两道保险：① `pmPress(accept = …)` 用 `inTopEndZone(点, 尺寸, CHECK_HIT_DP)` 在**几何上**把右上角 24×24 排除（半开区间，与格子严格互补）；② 红勾改用 `awaitEachGesture`，down 到手立刻 `consume()`，抬起必须仍在同一块区域（移出即取消，与系统复选框一致）。`PhotoHitZoneTest` 扫描整格验证"每像素只归一边"。

**`Ctrl`+点图 的加选已删除（v3.7）**：`PressModifiers` 只带 `shift`，`clickPhotoSelection` 也没有 `ctrl` 参数 —— 这不是"读不到修饰键所以降级"，而是**让点图在类型上就不可能走到"切换"分支**。修饰键读偏最多造成"Shift 连选退化成单选"（可接受），绝不会造成勾选集合错乱。

**`pointerInput` 的闭包坑（v3.5 修过）**：`pointerInput(Unit)` 的 block 只在首次组合时启动一次，之后既不复跑也不换 lambda —— 闭包里那份 `ui` 会永远停在"弹窗刚打开、还没勾选"那一帧。现在 `pmPress` 与红勾回调都用 `rememberUpdatedState` 转发，回调体里读的也是最新 `ui`（`PhotoSelectionTest` 盯住"连点五张必须得到五张""连点同一张两次不能把它 toggle 掉"）。

- "选"有两个落点，语义不重叠：`Shift` + 点（连选一段）、右上角红勾（逐张加选/减选，看得见的状态）。不碰键盘也能多选，习惯快捷键的人也不会误判。
- 不按 `Shift` 时清掉其它勾选，是为了避免"看着 A、却操作着一堆之前勾的"这种错觉。
- **区间连选的顺序取"当前可见顺序"**（`shown.map { it.id }`，即搜索过滤后的缩略条），不取 id 顺序、也不取 core 的 `photoIds` 顺序 —— 搜索只剩 3 张时，Shift 选的就是屏幕上这 3 张里的一段。
- **锚点不跟着 Shift 走**：`点 1 号 → Shift+点 5 号 → Shift+点 3 号` 的结果是 1~3，与资源管理器/Excel 一致；若锚点跟着走，第二次 Shift 就会从 5 号往回选，用户得重新找起点。
- **锚点缺失或已被过滤掉**（换了事件、搜过别的词）→ Shift 退化成普通点（单选）。宁可少选，也不要"从一张看不见的照片开始连选"。
- **红勾不改预览**：点第 5 张的红勾只改勾选，大图仍是正在看的那张。勾选（要对哪几张动手）与预览（我在看哪张）本来就是两件事，耦合起来会让人分不清"这一下改的是哪个"。
- 事件的缩略条与卡片**按拍摄时间升序**（`WorkQueue.sortedByCapture`，无时间的排最后、同刻按 id 兜底）；core 的 `photoIds` 顺序不动 —— 它还决定导出文件名序号与台账的"照片1/照片2"。

### 6.2 快捷键（日历除外）

| 键 | 作用 | 等价入口 |
| --- | --- | --- |
| `F5` | 分析；已有结果时先问「要重新分析吗」 | 日志条旁「开始分析」 |
| `Ctrl+O` | 导入 `.txt` 日志 | 输入框右上「导入」 |
| `Ctrl+E` | 导出；条件不满足时给出原因（与顶栏同一判定） | 顶栏「导出」 |
| `Ctrl+,` | 打开设置 | 顶栏「设置」 |
| `Esc` | 有关闭覆盖层就关掉它；否则清空勾选 | 弹窗右上角 ✕ |
| `Ctrl` + 点缩略图 | 加选/减选（§6.1） | 缩略图右上角方格 |
| `Shift` + 点缩略图 | 从锚点连选一段（§6.1） | —（逐张点方格等价，只是慢） |

两条原则：

1. **键盘只是加速，不是唯一入口。** 上表每一行都有点得到的位置，所以状态栏右下角仍然写按键表；这也意味着按键失效（比如焦点在文本框里被吞）不会让人走不下去。
2. **日历不吃键盘**（§6.3）：这是全项目唯一的例外，日期格子与日期字段都走 `pmPress`（`pointerInput`）而不是 `clickable`，因此没有 focus 节点 —— `Tab` 进不来、`Enter`/`Space` 不会选中日期、方向键也不会在网格里移动。

## 为什么日历单独例外

网格键盘导航要自己维护"光标落在哪一格、跨月时怎么翻、回车与空格分别代表什么、焦点进入面板时初始落在哪天"，而日期是**一次性选择**（选完面板就关），不值得为它养一套几乎没人用、却要长期走查的交互。选日期只有一条路：用鼠标点格子 —— 这条路的错法已经被控件形状挡掉了（格子足够大、补位日淡色可辨、选中态靠底色 + 描边双标）。

面板里的「翻月 `‹` `›` / 今天 / 关闭」是普通按钮，与别处同一个 `PmButton`，不在此列 —— 它们不承担"在日历里移动选中项"。

**没有 `Ctrl + Z`**：core 不提供 undo，人工调整只能「全部重置」（设置层）。与其做半可信的撤销，不如把重置写明白（照片层固定一句"改动立即生效，不需要重新分析"）。

### 6.3 日期选择（只在主页，只用鼠标）

日期列在 `LogBar` 左侧，日历是**浮层**（根覆盖层，不参与页面布局）；**只响应鼠标**（不做 `←/→`/`Enter`，见 §6.2 末段）。

| 操作 | 结果 |
| --- | --- |
| 点日期字段 | 展开/收起日历浮层（`datePickerOpen` 在 `UiState`：面板画在根覆盖层，得由持有状态的一方决定画不画） |
| 点浮层外面 / `Esc` | 关闭；`Esc` 的层级顺序是"日历 → 弹窗 → 照片勾选" |
| 点某一天 | 立即写入 `patrolDate` 并关面板；补位日（上下月）点了会跳到那个月 |
| `‹` / `›`（面板内） | 翻月；跨年由 `YearMonth.plusMonths` 处理，不手写 12/1 边界 |
| 前一天 / 后一天 | 按天步进（现场最常见的是"补看昨天"） |
| 今天 | 回到当天；面板里"今天"用强调描边标出（选中时只靠底色区分） |
| 回今天（面板内） | 只在"今天不在当前显示月份"时出现，避免和标题重复 |

**浮层的三条定位规则**（`ui/dialog/DatePickerLayer`）：① 左边缘对齐日期字段并夹在窗口内（右留 8 dp）；② 默认长在字段下方 6 dp；③ 下方放不下就翻到字段上方，仍放不下则贴窗口下沿。位置用的是**窗口像素**，所以 100% / 125% / 150% 缩放不需要另算一套。

为什么不用 Compose 的 `Popup`：桌面端它是否走独立 OS 窗口随版本/属性变化，一旦走独立窗口就重演 §2.4 的 DPI 事故。根覆盖层里的绝对定位卡片，坐标就是主窗口像素，行为完全可预期。

日历**不做年视图**：翻 12 次也就一秒，而年视图会把面板撑高一倍、在小窗口里被裁。也**不做手输**：这套字段的错法都是"静默无效"（敲成 `2026-13-01` 后界面把输入吞掉），把输入口关掉比做一套校验提示更省事。

### 6.4 照片搜索

| 操作 | 结果 |
| --- | --- |
| 操作条左侧搜索框 | 按**文件名**（忽略大小写）、**拍摄时刻**（`08:3`、`08`）过滤缩略条 |
| 输入「无时间」 | 只留 `captureTimeMs == null` 的照片（它们是一类真实数据，用户会专门去找） |
| 有搜索词时 | 搜索框右侧显示命中数 `3/8` + 「清除」；缩略条为空时给"没有匹配「…」的照片" |
| 关闭再打开弹窗 | 搜索词自动清空（否则会看到一个"少了几张"的列表，而搜索框已不在视野里） |

搜索只作用在**当前事件的缩略条**上，不影响大图、不影响台账两格、不调用 core —— 它是纯视图过滤（`model/PhotoSearch.kt`，6 个用例）。

### 6.5 反馈时机

| 场景 | 反馈 |
| --- | --- |
| 按钮不可用 | 按钮禁用 + 就地一行原因（如"先粘贴日志或选择源目录"） |
| 分析/导出中 | 覆盖层：阶段名、计数、进度条、取消 + 取消语义说明 |
| 照片调整 | 无 toast，界面直接变（卡片张数、角标、事实栏） |
| 归属调整的**失败/未生效** | 顶部一条结果通知（§6.6）：是什么、为什么没生效、下一步点哪 |
| 失败 | 顶栏下错误条，可逐条收起（记住收起的是哪一条，不是布尔） |
| 导出完成 | 顶部结果条，可收起，状态栏留「上次导出 N/M」入口重看 |

### 6.6 主页面缩略图的移动 / 复制 + 结果通知

**入口藏在悬停里**：鼠标移到某个照片格上，格子上蒙一层半透明深底，里面是「移动」「复制」两个按钮
（15 dp 图标 + 10 sp 文字竖排）。未匹配池的格子只给「移动」—— 它没有归属事件，复制会让它同时出现在两个地方。

| 为什么这么做 | 说明 |
| --- | --- |
| 不常驻显示 | 72 dp 的格子常驻两个按钮就没有地方放照片了，而"这是哪张"（时刻）才是卡片的第一信息；扫视时看到按钮还会误以为"这张正在被操作" |
| 也不做成右键菜单 | 右键菜单不可发现，且要在窗口坐标里自己定位、处理贴边翻转；悬停层的落点就在被操作的那张图上，不需要额外解释"这是对谁做的" |
| 按钮带文字 | 只给图标的话"两只箭头=移动、两张纸=复制"是猜的，猜错一次就是一次误移动 |
| 按钮用 clickable | 它会消费按下事件，所以点按钮不会顺带打开整个事件的照片弹窗 —— 一次点击仍然只做一件事 |

**执行前先问"能不能做"**（`model/Feedback.rejectReason`，13 个用例）：

| 情况 | 拦截时的说法 |
| --- | --- |
| 目标就是它现在所在的事件 | 候选列表已经排除，不选它（唯一性校验落在列表上，不落在报错上） |
| 复制时目标已全部持有 | 「目标事件已经有这 N 张了，不重复添加」 |
| 选中的照片里有未匹配照片（复制） | 「未匹配照片不能复制，先移到某个事件里」 |
| 照片已经不在结果里 / 目标事件不在结果里 | 「请重新分析后再调整」 |
| 导出还没结束 | 「导出还没结束，结束后才能调整归属」（core 此时会静默拒绝，界面必须先说） |

**执行后按回来的数字说话**：core 的 `movePhotos` 与 `copyPhotos` 都返回**真正生效的张数**
（所以在"目标就是它现在的家"这种什么都没发生的情况下，界面不可能再假装成功）。界面据此三选一：说成功了 + 目标名（`OK`，绿） /
说部分没生效的原因（`OK`，但写明"另 N 张该事件已有"）/ 说为什么没生效（`WARN`，黄）。
成功后会清掉 core 那条简短 message —— "已移动 1 张照片"和"已把 1 张照片移到 事件 03 · 中山路"
同现等于同一件事说两遍，反而让人不确定发生了几件事。

**为什么要有 tone 这个字段**：同一个位置要显示"成了 / 没生效 / 出错"三种结果，全用灰条的话
用户只能靠读字判断；而这三件事必须一眼分开。语气属于数据（`LocalNotice(text, tone)`），不由界面猜。

## 7. 响应式

### 7.1 窗口

```
默认 1440×900 dp，最小 900×540 dp
下限 = min(540, 工作区高)；上限 = max(下限, 工作区高×0.9)；再 coerceIn
```

顺序不能反：1366×768 @125% 的工作区是 1093×574，`0.9×574=517 < 540`，直接 `coerceIn(540, 517)` 会抛空区间，**崩在启动阶段**。已有 10 个用例覆盖（含 640~3840 × 480~2160 全扫描不出界）。

| 物理分辨率 | 缩放 | 实际开出 | 内容宽 | 照片格 |
| --- | --- | --- | --- | --- |
| 1366×768 | 125% | 984×540 | 970 | 80 |
| 1366×768 | 100% | 1229×655 | 1215 | 88 |
| 1920×1080 | 100% | 1440×900 | 1426 | 96 |
| 1920×1080 | 150% | 1152×612 | 1138 | 88 |

照片格四档 `96 / 88 / 80 / 72`，按内容宽取；一行格数 `((可用宽+8)/(格+8)).coerceIn(1,10)`，超过 10 张用「+N」收尾（实测每个事件 1~5 张，10 格已经够用）。

卡片栅格（四条都是常量，不随窗口变，单测盯住）：

| 项 | 值 | 作用 |
| --- | --- | --- |
| 序号列 | 26 | 1 位数与 2 位数都占满，卡片之间序号不左右抖 |
| 时间列 | 96 | 放得下 `08:15–08:30`；未匹配卡留空也占位，保证标题同列 |
| 张数列 | 56 | 右对齐，`1 张`与`12 张`的个位在同一竖线上 |
| 头部行高 | 30 | 有标签（20 dp）也能垂直居中 |
| 无照片占位行 | 40 | 高度随内容，但左边缘/圆角/底色与照片条一致 |

高度差：同一屏里 `cardHeight(80)=146`、`emptyCardHeight()=106`。

### 7.2 弹窗

- 宽 `(窗口宽-56).coerceIn(640, 1040)`，高 `(窗口高-48).coerceIn(420, 720)` —— 永远落在窗口内（已单测扫 8×7 组尺寸）。
- 900×540 的窗口 → 弹窗 830×455：大图区 530、侧栏 300（v3.7 起，用于"巡查日志内容"）、缩略条 72、操作条 42 → **大图高 300**（v3.1 是 ~229）。
- 1366×740 的窗口 → 弹窗 1040×692：缩略条 92 → 大图高 **517**（v3.1 是 ~380）。
- 弹窗高度永远取 `min(520, dialogHeight(窗口高))`：早期版本用 `+40` 想"高一点好放列表"，结果底部越过窗口下沿，最后一行被切成半行且抓不到滚动条。
- 侧栏阈值 760：低于此宽度就把事实折到下方（当前最小窗 830 仍在阈值之上，所以侧栏常驻）。

## 8. 一致性规则

1. **一个状态来源**：`CoreStatus` 决定所有 enabled 与文案。
2. **一个口径**：`WorkQueue` / `LedgerJoin` / `Layout` / `reduce` 是唯一实现，Composable 不写业务算术。
3. **一个强调色**：不同时出现在三处以上。
4. **动作不隐藏**：日志框收起必须留「重新分析 / 重新输入」；卡片放不下用「+N」而不是横向滚动。
5. **长任务必有出口**：超过 1 秒的操作都有进度、计数、取消与取消后果说明。
6. **不重复文案**：一张卡片里"无照片"只出现一次（标签），不再配"0 张"。
7. **折叠线上不硬切**：能滚的区域必须有条；装得下就别画；只差几像素也别画。
8. **"统一"落在栅格上，不落在像素等高上**：同一字段的列宽、行高、左边缘必须一致（卡片头部 26/96/56），但区块高度随内容变化——强行等高只会把空占位撑成一张缩略图的面积。
9. **一个事实只说一次颜色**：卡片有照片＝红框；"无照片"就不再配红字、不再配"0 张"。红在同一个卡片里只能有一个含义。
10. **动作必须有鼠标入口**：快捷键只是加速，任何一个键都要有可见可点的等价入口；新增能力必须同时给出入口的落点（按钮/格子/行内链接），否则等于没做。日历是例外，它只有鼠标入口，也不打算有键盘入口。
