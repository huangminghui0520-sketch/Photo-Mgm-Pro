# Windows 桌面端界面规格 v2.0

> 适用模块：`desktop/ui`
> 依据：`desktop/core` 已冻结的 `PhotoMgmCore` 接口与其 359 个通过测试所固定的行为语义（ui 另有 40 个）
> 状态：已实现（U2），本文档为实现的对应说明，不是待做的设计稿
> 替代：本文件 v1.0（U1 三栏骨架）已删除，理由见 §0

---

## 0. 为什么推倒重来

v1.0 是「先画三栏，再往里塞东西」：左栏放源目录、日志、设置，中栏放事件列表，右栏放照片网格。三栏在视觉上平衡，但和 core 的实际语义对不上。以下五处不是配色或间距问题，是结构问题：

| 旧结构 | core 的实际语义 | 后果 |
| --- | --- | --- |
| 左栏固定 300 dp 放输入项 | 源目录、日志只在第一步输入一次，后四步完全不看 | 100% 的宽度里 30% 长期闲置，而真正需要宽度的照片网格被压到中栏 |
| 事件与照片并排成两栏 | `EventSnapshot.photoIds` 是事件的**字段**，照片没有独立归属 | 用户必须自己做心算 join：左边第 3 行对应右边哪些缩略图？ |
| 一个 `analyze()` 拆成「扫描目录」「读取日志」两个按钮 | `analyze()` 是单次原子流水线，内部 7 步不可分割 | 界面上存在两个都点不动的按钮，以及「点哪个」的困惑 |
| 「去重模式」写成持久设置并配保存按钮 | `setDedupMode()` 同步重算视图，**不重新扫描**，是视图参数 | 默认用户会以为改了设置必须重新分析，于是反复分析 |
| 导出按钮在顶部全局工具条 | 导出依赖「已选输出目录 + READY 状态 + 无阻塞项」，是流程末端的动作 | 输入还没完成时按钮亮着，点了弹错误 |

结论：本次做法相反 —— **先读 core，把业务流程、数据流向、状态机、动作语义梳理清楚，再决定界面有几个区域、每个区域回答什么问题。**

## 1. 运行逻辑梳理

### 1.1 业务流程（实际发生的事）

```
选巡查日期 ──┐
加源目录   ──┤
粘贴/导入日志┴─→ analyze() ─→ 台账（N 个事件 + 未匹配池）─→ 人工确认 ─→ export() ─→ 产物
                                    ↑                                        │
                                    └──── 移动照片 / 指定台账照片 / 重置 ───────┘
                                          （不重新分析，立即生效）
```

关键点：

1. **一个巡查日 = 一个项目 = 一次导出。** 日期不是筛选项，是项目主键；换日期等于换项目。
2. **分析是一次性的重活**（解析 → 扫目录 → 粗筛 → 去重 → 读 EXIF → GPS 聚类 → 分类），后续所有人工调整都在内存模型上做，**不触发重扫**。
3. **人工调整只有三个动作**：把照片移到某个事件、把某张照片指定为台账的第 1/2 格、全部重置。没有第四种。
4. **导出是副本操作**，源文件不动。取消导出不清空已复制的文件，下次按 manifest 续传。

### 1.2 数据流向

```
日志文本 ──parseLog──→ 日志事件（有地点/描述/时间窗，无照片）
                            │
源目录 ──scan──→ 照片文件 ──粗筛(文件名日期)──→ 候选
                            │
                    去重(content hash) ──→ 派生副本标记
                            │
                    EXIF 批读(25/批) ──→ 拍摄时间 + GPS
                            │
                    GPS 时段聚类 ──→ 归属到日志事件
                            │
                    分类 ──→ events(行) + photos(平表) + unmatchedPhotoIds
```

产物形状：

- `state.events`: `List<EventSnapshot>`，**保持日志顺序**（第 1 条日志 = 第 1 个事件）
- `state.photos`: `Map<Long, PhotoSnapshot>` 扁平表，照片不认识事件
- `state.unmatchedPhotoIds`: 有文件但没归到任何事件的照片
- 一条事件 = 台账一行 = 导出一个文件夹 `NN_地点描述/`；未匹配 = `99_未分类/`

两个必须先知道的坑：

1. **台账生成时用 `events.sortedBy { endTimeMs }` 排序，而 `state.events` 是日志顺序。** 两者行序不同，不能按下标配对。UI 必须按 `(location, description)` 顺序消费配对 —— 见 `model/LedgerJoin.kt`。
2. **`photoIds` 只保证「属于这个事件」，不保证台账格子顺序。** 台账第 1/2 格由 `markLedgerPhoto` 指定，未指定时取排序后前两张。

### 1.3 状态机（core 只有 6 个状态）

| CoreStatus | 含义 | 谁进入 | 谁能离开 |
| --- | --- | --- | --- |
| `IDLE` | 有设置、无结果 | 启动 / 清空 | `analyze()` |
| `ANALYZING` | 分析中，可取消 | `analyze()` | 完成 → `READY`；取消/失败 → `FAILED`→`READY` 由 core 决定 |
| `READY` | 有结果，可编辑可导出 | 分析完成 / 导出完成 / 人工调整 | `analyze()` / `export()` |
| `EXPORTING` | 导出中，可取消 | `export()` | `READY` + `lastExport` 更新 |
| `FAILED` | 上一步出错，`message` 有文本 | 任意失败 | 下次操作 |
| `CLOSED` | 已释放 | `close()` | — |

**注意：没有 `EXPORTED` 状态。** 导出成功后回到 `READY`，结果在 `state.lastExport` 里。所以「导出完成」这件事必须由 UI 自己用**边沿检测**识别（比较 `lastExport.exportDir` 是否变化），不能等状态。

### 1.4 模块交互与 UI 边界

`ui` 只允许依赖三个文件：`api/PhotoMgmCore.kt`、`api/AppState.kt`、`api/ExportModels.kt`。core 的 12 个方法全部是命令式调用，返回 `OperationHandle` 或 `Boolean`，**没有回调驱动 UI 的通道**，唯一的观察面是 `StateFlow<AppState>` 全量不可变快照。

这条约束直接决定了 UI 架构：

```
core.state: StateFlow<AppState>  ──┐
                                   ├─→ reduce(ui, state) ─→ UiState ─→ 渲染
用户输入 ─→ Actions ─→ core.xxx() ─┘        ↑ 纯函数，可单测，幂等
```

`UiState` 是 `AppState` 的**投影**，不是它的副本：`reduce` 不产生副作用、不调 core、可以重复调用同一次输入得到同一结果（已单测）。

### 1.5 用户操作路径（真实路径，不是理想路径）

1. **首次**：打开 → 选日期 → 加 2~4 个源目录 → 粘贴或导入日志 → 点「开始分析」→ 等（2~20 s）→ 看到台账。
2. **确认**：逐条看事件 → 看到「无照片」「无时间」「N 条提示」标记 → 点进去看照片 → 把漏归的照片拖/移到正确事件 → 偶发需要指定台账封面格。
3. **兜底**：翻「未匹配照片」池（通常 5~40 张）→ 能归的移走 → 剩下的接受它们进 `99_未分类`。
4. **导出**：确认输出目录 → 选校验强度 → 导出 → 看结果页 → 打开目录交付。
5. **返工**：发现时间窗错了 → 改日志 → 重新分析（**会丢弃全部人工调整**，需二次确认）。

路径长度决定了界面形态：第 2 步占 80% 时间，所以 REVIEW 是主轴；第 1 步只做一次，可以收窄。

## 2. 由逻辑推导出的九条结构决策

### 2.1 四个阶段，而不是一个工作区

- **依据**：业务流程是 `输入 → 分析 → 确认 → 导出`，`CoreStatus` 天然把「分析」和「导出」标成独立状态，且这两步都是长任务、都可取消。
- **结论**：界面是 4 个互斥的 stage（`INPUT / REVIEW / EXPORT / RESULT`）+ 1 个 `Busy` 覆盖层。左侧 64 dp 竖排步骤条常驻，显示 3 步和当前位置；`RESULT` 不是第 4 步，它是导出之后的结果态，挂在 EXPORT 步骤下，所以步骤条只有 3 个圆点。
- **不允许**：同一屏同时呈现输入区和照片网格。那正是 v1.0 的错误。

### 2.2 事件是工作单元，照片是它的附件

- **依据**：`EventSnapshot.photoIds` + `eventPhotoIds` 的父子关系；一个事件 = 台账一行 = 导出一个文件夹。
- **结论**：REVIEW 里左列是事件（含「未匹配照片」固定行），中间是**当前事件**的照片，右侧是**当前事件**的检查器。三者共享同一个 `Selection`，界面上不存在「这些照片属于谁」的歧义。
- **代价与取舍**：不能同时看两个事件的照片。实测这没有损失 —— 用户的真实动作是「比对事件 A 有没有漏照片」，比对时看的是日志文本和照片时间，不是另一个事件。

### 2.3 分析只有一个入口

- **依据**：`analyze()` 是原子流水线，7 步不可分割。
- **结论**：一个按钮，文案随状态变（`开始分析` / `重新分析`），下方一行灰字列出 7 步顺序，让用户在点之前知道它要干什么。没有「扫描」和「解析」两个按钮。
- **`重新分析` 的二次确认**：因为会丢弃人工调整，且不可撤销（core 无 undo），点击后弹确认，说明会丢什么。

### 2.4 去重模式是视图开关，不是设置

- **依据**：`setDedupMode()` 同步重算，不重新扫描。
- **结论**：放在 REVIEW 工具条上，做成 `Segmented`（全部 / 保留原始），旁注「切换不重新扫描」。**不写进设置面板，不加保存按钮。**

### 2.5 导出只在流程末端，且自己检查前置条件

- **依据**：`export()` 需要 输出目录 + READY + 有事件。
- **结论**：导出步骤单独一屏，先列产物（N 张照片 + M 张未分类 + 台账 csv）再给按钮；阻塞项用 `InlineNotice` 直接写出来（「还没有设置导出目录」+ 就地「选择目录」），而不是让用户点了才知道。全局工具条上没有导出按钮。

### 2.6 结果页是独立 stage，不是弹窗

- **依据**：`ExportResult` 含 `totalTargets/copied/skipped/failed/durationMs/failures/warnings/ledgerWritten`，信息量远超一个 toast；且 core 没有 `EXPORTED` 状态，不主动呈现就没有机会呈现。
- **结论**：导出成功后 `reduce` 检测到 `lastExport.exportDir` 变化 → 切到 `RESULT`。四种结局（已取消 / 有失败 / 已续传 / 全部完成）用同一个 `Headline` 组件不同 tone 表达，下方是统计格 + 产物清单 + 失败明细（最多 30 条）。

### 2.7 长任务的取消语义必须写在屏幕上

- **依据**：`OperationHandle.cancel()` 对分析和导出的效果不同 —— 分析取消丢弃本轮结果；导出取消保留已复制文件，下次续传。用户最怕的就是「取消了，我的文件是不是坏了」。
- **结论**：`BusyOverlay` 里按 `Busy.step` 显示不同文案，取消按钮旁固定一句话说明后果。

### 2.8 未匹配池是一等公民，不是垃圾桶

- **依据**：未匹配照片是真实存在的、必须交付的东西（进 `99_未分类/`）。
- **结论**：它固定占事件列表的最后一行，带计数徽标，点进去有独立检查器（可以「全选未匹配」再批量移走）。`ReviewFilter.UNMATCHED` 是 5 个筛选项之一。

### 2.9 所有口径只算一次

- **依据**：v1.0 里「待确认」在工具条、状态栏、事件行各算一遍，三个地方的数字一度不一致。
- **结论**：`model/WorkQueue.kt` 是审核语义的唯一来源（`needsReview` / `issueLabels` / `stats` / `filter` / `exportBlockers`），Composable 里不允许出现业务判断。`model/Layout.kt` 同理（所有宽度、列数、断点）。**理由**：口径重复实现，最终一定出现「界面说 7 个事件，台账 8 行」。这些函数全部有单测（36 个用例）。

### 4.1 颜色（附实测对比度）

- 语义色只出现在 `Tag` / `FilterChip` / `InlineNotice` 里，不做背景大色块。

- 状态色不承担「可点」语义，可点只由 hover 底色 + 光标表达。

## 6. 交互

### 6.1 选择模型

- **单选**：事件列 / 未匹配行 / 照片。点空白清除。
- **多选**：`Ctrl + 点击` 照片加选；`Ctrl + A` 选当前视图全部照片。
- **不做 Shift 连选**：照片网格是多列布局，连选的「区间」定义有歧义；`Ctrl+A` 已覆盖真实需求（整批移走）。
- 多选是**照片维度**的，与事件选择正交：切事件保留照片多选？**不保留** —— 跨事件移动无意义，切事件时清空。

### 6.2 快捷键

| 键 | 动作 | 作用域 |
| --- | --- | --- |
| `F5` | 开始/重新分析 | INPUT |
| `Ctrl + O` | 导入日志 .txt | INPUT |
| `Ctrl + E` | 进入导出 | REVIEW 且有事件 |
| `Ctrl + A` | 全选当前照片视图 | REVIEW |
| `Esc` | 收起提示 / 关抽屉 / 退多选 | 全局 |

**没有 `Ctrl + Z`。** core 不提供 undo 栈，人工调整只有「全部重置」一个回退。与其做一个半可信的撤销，不如把重置做得明确（检查器里一句话：「改动立即生效，不需要重新分析」）。

### 6.3 反馈时机

| 场景 | 反馈方式 | 时长 |
| --- | --- | --- |
| 点按钮无反应（前置不满足） | 按钮禁用 + 就地灰字说明原因 | 常驻 |
| 分析/导出进行中 | `BusyOverlay` + 进度条 + 计数 | 直到结束 |
| 人工调整生效 | 无 toast，界面直接反映（列表徽标、计数、检查器同步变） | 即时 |
| 操作失败 | 顶栏下 `InlineNotice(danger)`，可逐条收起 | 常驻至下次操作 |
| 界面自己的提示 | `localMessage` → 同位置 info 条 | 常驻 |

人工调整**不做 toast**：它每秒可能发生十几次（批量移动），toast 会盖住照片。界面本身的变化就是反馈。

## 7. 响应式

### 7.1 窗口策略

```
默认 1440×900 dp，最小 900×540 dp
下限 = min(540, 工作区高)
上限 = max(下限, 工作区高 × 0.9)
初始高 = clamp(900, 下限, 上限)     ← 顺序不能反
```

必须先把下限压到工作区以内再 clamp，否则 1366×768 @125%（工作区 1093×574，0.9×574=517 < 540）会抛 `IllegalArgumentException: Cannot coerce value to an empty range`。该场景已有单测（`WindowGeometryTest`，10 个用例，含 640~3840 × 480~2160 全扫描不出界）。

窗口位置尺寸记忆（M6b）读回后同样过一遍 clamp，然后判断是否仍与某块屏幕相交，否则回落默认值并居中。

### 7.2 REVIEW 三区收敛

| 内容宽 | 事件列 | 检查器 | 网格宽 | 列数 |
| --- | --- | --- | --- | --- |
| ≥ 1380 | 280 内联 | 320 内联 | 其余 | 5~7 |
| 1100 ~ 1379 | 260 内联 | 抽屉 | 其余 | 4~5 |
| 900 ~ 1099 | 240 内联 | 抽屉 | 其余 | 3~4 |
| < 900 | 0 折叠 | 抽屉 | 其余 | 2~4 |

- 最小宽 900 时内容宽 886：事件列折叠、网格 821 dp / 4 列、检查器走抽屉。
- **事件列折叠后必须留替代入口**：照片区顶部的 `EventPicker`（`3/8 切换事件 · 4 待确认`），否则折叠等于删掉了一个动作。
- 网格列数 `((gridW + 12) / (168 + 12)).coerceIn(1, 7)`，单块最小 168 dp。**永远不出横向滚动条** —— 宽度不够就减列。
- 宽度守恒有单测：`railW + 分隔线 + listW + gridW + inspectorW == 内容宽`，7 dp 步长扫 640~3840 全部成立。

### 7.3 INPUT 与 EXPORT

| 阶段 | 断点 | 行为 |
| --- | --- | --- |
| INPUT | 内容宽 ≥ 860 | 双栏（素材 340 / 日志自适应）；≥ 1100 时素材 392 |
| INPUT | < 860 | 单栏纵排（此时 540 高度下日志框会折到下方，允许） |
| EXPORT | 内容宽 ≥ 1180 | 左侧选项 320 + 右侧表格 |
| EXPORT | < 1180 | 选项收成顶部横条，表格占满 |
| EXPORT 表格 | 表宽 < 920 | 紧凑列：结束时间只留 `HH:mm`（44 dp）、照片只显示文件名、第二张同文件显示「同上」 |

紧凑列的取舍：宁可少显示一层目录名，也不能让 `01_1101_到达上行K1…` 这种被截断的路径占满一列 —— 那是「有信息但读不出来」，比没有更糟。

## 8. 一致性规则

1. **一个状态来源**：`CoreStatus` 决定所有 enabled / 文案；UI 不推断「大概完成了」。
2. **一个口径**：`WorkQueue` / `LedgerJoin` / `Layout` / `reduce` 是唯一实现，Composable 不写业务算术。
3. **一个强调色**：赭橙只用于主行动点和选中态，不同时出现在三处以上。
4. **一套间距**：只用 2/4/6/8/12/16/24/32，不写 `7.dp`、`13.dp`。
5. **一种徽标语义**：`Tag` 的 tone 固定映射 —— `warn`=需要人看（无时间/提示）、`danger`=缺失（无照片）、`info`=中性计数、`accent`=当前。
6. **动作不隐藏**：区域可以折叠，但折叠必须给出替代入口（`EventPicker`），不允许某项能力因宽度不足而消失。
7. **长任务必有出口**：任何超过 1 秒的操作都有进度、计数、取消。

对照关系：

- §2 的决策 ↔ `model/` 的函数名（决策 2.9 直接对应 `WorkQueue.kt` 的存在）

## 10. 交付形式与适用范围

### 交付物

| 交付物 | 位置 | 用途 |
| --- | --- | --- |
| 本文档 | `docs/WINDOWS-DESKTOP-UI-SPEC.md` | 结构决策与运行逻辑的对应关系 |
| 实现 | `desktop/ui/src/main/kotlin/...`（29 文件 / 5130 行） | 唯一事实，文档与实现冲突时以实现为准 |
| 单测 | `desktop/ui/src/test/...`（5 文件 / 519 行，40 用例） | 布局、状态归约、审核口径、窗口尺寸的回归保护 |
| 证据截图 + 渲染日志 | `desktop/ui/build/shots/` | 各断点真实 `AppState` 的渲染结果 |

### 验证命令

```bash
./gradlew :ui:test                                   # 40 用例
./gradlew :ui:run --args="--demo --shot out.png --log-file out.log"
./gradlew :ui:run --args="--demo --size 900x540 --stage review --shot r.png"
```

`--demo` 会生成带真实 EXIF（时间 + GPS）的 JPEG，跑真实 `analyze()`，所以界面渲染的是真 `AppState`，不是假数据。

### 为什么没有 Figma 稿

1. 界面是**规则驱动**的：所有宽高在 `Layout.kt`，所有颜色在 `Tokens.kt`，一张静态图反而会成为第二个事实来源，容易和代码漂移。
2. 关键约束是**连续量**（900~3840 之间任意宽度都不能出滚动条），静态稿只能画出几个离散点。
3. 真实数据形状（8 个事件 / 12 张照片 / 2 张未匹配）比设计稿里的 Lorem 更能暴露问题 —— 本版 6 处缺陷（列溢出、路径截断、日期行裁切、表格挤压、状态栏出血、无事件切换入口）全部是看真实截图发现的，不是看图发现的。

### 不适用范围

- 本文档不定义平板/移动端形态（无此计划）。
- 不定义深色主题（当前只实现浅色，`Tokens` 已按可换肤组织，但未做第二套值）。
- 不定义缩略图加载策略（U1.3 待接口签名评审；当前是稳定占位符）。

## 11. 已知缺口

| 缺口 | 影响 | 计划 |
| --- | --- | --- |
| 无缩略图，只有占位块 | 用户无法凭图像判断漏拍/错归，只能看文件名和时间 | U1.3，需先定 `ThumbnailProvider` 接口签名与受控加载语义 |
| 无拖放 | 移动照片需两段式，批量场景慢 | 待评估；两段式已能完成任务 |
| 无撤销 | 误移动只能「全部重置」再重来 | 依赖 core 增加 undo 栈，本版不做 |
| 深色主题 | 夜班不友好 | Tokens 已分层，加一套颜色值即可 |
| 分析进度无总量 | 进度条走「不定量」样式（整块浅色填充） | core 未上报总文件数 |
| 导出失败明细上限 30 条 | 大规模失败时看不全 | 结果页提供「打开 export.log」 |
