> 发现于 **2026-11-02**，用真实素材（`C:\Users\28988\Desktop\ceshi` → 真机 `/sdcard/Pictures/pmgolden-real`）
> 跑首次端到端验证时暴露。**合成素材完全测不出来**——这是它第一次被真实数据击中。

## 1. 现象：110 张素材，只导出 54 张

真机解析→导出跑通，摘要一切正常（33 事件 / 110 照片 / 未匹配 0 / 台账 33 行），
但 ZIP 里只有 **54 张**照片。素材结构是 **55 张主图 + 55 张 `_original` 副本**，
按"仅保留带水印"应输出 55 张。**少 1 张**。

逐张比对定位到缺失的是 `IMG_20261024_153742079.jpg`（15:37:42 的 K152+200M 过车涵洞）。
而且它**连同自己的副本一起消失**：

| 文件 | 时间戳 | 结果 |
| --- | --- | --- |
| `IMG_20261024_153741122.jpg` | 15:37:41.122 | ✅ 进了 ZIP |
| `IMG_20261024_153741123_original.jpg` | 15:37:41.123 | 被合并（正确） |
| `IMG_20261024_153742079.jpg` | 15:37:42.079 | ❌ **消失** |
| `IMG_20261024_153742081_original.jpg` | 15:37:42.081 | 随主图一起消失 |

## 2. 根因：判重只看「场景相同」，没看「同一张照片」

`ExifContentDedupStrategy.isSame` 的 GPS 有效分支是：

```kotlin
if (abs(ta - tb) > timeToleranceMs) return false      // 时间 ±1s
return haversineM(latA, lngA, latB, lngB) <= gpsToleranceM   // GPS ≤10m
```

**这两条都是"在同一地点、同一时刻"的证据，不是"这是同一张照片"的证据。**
一个人站在同一个位置连按快门，两张不同照片的拍摄时间与 GPS 必然都近乎相同。

实测这四张的元数据：

| 对比 | 时间差 | GPS 距离 | 内容（sha256） |
| --- | --- | --- | --- |
| `153741122` ↔ `153742079` | **957 ms** ≤ 1000 | **2.74 m** ≤ 10 | **不同**（差 37 KB，1,347,425 vs 1,309,983 B） |
| `153741122` ↔ `153741123_original` | 1 ms | 0 m | 不同（一个是水印版、一个是原图） |

两个条件都满足 → 判为"同一张" → `retain` 选 `153741122` 当代表 → 其余三张全部丢弃，
其中包括**一张有独立内容的真实照片**。

### 2.1 这道防线 10 月 24 日修过一次，但挡住的是另一种情形

`groupDupContent` 里原有的注释写着：

> ★ 2026-10-24 修复（真实数据验证发现）：禁止链式传递合并。
> 并查集会把"相邻两个瞬间各自的双份"误并成 4 张一组，导致误删另一瞬间的真实照片（15:37 过车涵洞实测被并组）。
> 改为「新照片须与组内**每一张**都满足判重才入组」——1s 容差下同一瞬间的 2 张双份可合并，
> 相邻瞬间（间隔 >1s）不会跨组合并。

当时的判断前提是"**相邻瞬间间隔 >1s**"。这次的实测间隔是 **957ms**，
即 A 与 C **本身就满足** `isSame`——不是经由 B 传递过去的。
所以"逐张都要满足"这条约束对它完全无效：它确实是"直接"满足的。

配套的回归测试也没抓到，因为它构造的数据是：

```kotlin
val a = photo(1, "..._153737864.jpg", t0)
val b = photo(2, "..._153737865_original.jpg", t0 + 1_000)
val c = photo(3, "..._153739389.jpg", t0 + 2_000)   // ← A 与 C 差 2000ms，刚好在容差外
val d = photo(4, "..._153739391_original.jpg", t0 + 2_000)
```

`+1000 / +2000` 恰好卡在 1000ms 容差的外侧，于是"通过"。
**测试用自己的假设验证了自己**：它假设相邻瞬间间隔必然 >1s，而真实连拍就是 <1s。

## 3. 最小修复：锚点 + 派生就近附着

不改阈值（1s / 10m 是用户可感知的语义，调小会漏并真双份，调大会误删更多），
而是**改用结构性约束**，让"一张主图被当成别人的副本"在结构上不可能发生：

| 概念 | 定义 | 规则 |
| --- | --- | --- |
| **锚点** | 不带派生后缀的照片（带水印主图） | 锚点之间**永不合并**——两张都有水印，就一定是两次独立的拍摄或保存 |
| **派生** | 带 `_original` / `_compressed` 等后缀 | 挂到「满足 `isSame` 且**文件名序号差最小**」的锚点上 |

"序号差最小"是关键：水印相机双份的毫秒序号差是 1~2，而相邻瞬间的主图序号差 ≈ 时间差（数百毫秒），
所以"最近"就是"自己的那一份"。

`isSame` 本身**一行未改**——它仍然负责回答"这两张是不是同一场景"，
只是不再独自决定"要不要合并"。

### 3.1 有意接受的代价（都朝"多留一张"方向）

| 情形 | 旧行为 | 新行为 | 判断 |
| --- | --- | --- | --- |
| 两张都**不带**后缀的真正重复（用户手动复制的副本） | 合并 | **不合并**，多留一张 | 可接受：宁可多一张，不可少一张 |
| 派生与锚点序号差 > `seqTolerance`(1000) | 合并 | **不合并**，多留一张 | 同上 |

去重的目的是"别让用户看到重复"，而不是"尽可能删得干净"。
**一次误删是不可恢复的（ZIP 里没有、原件也不在输出里），一次漏并只是多一张。**
这个取舍写进了代码注释，避免后人把"漏并"当 bug 又调回去。

## 6. 影响面

| 场景 | 影响 |
| --- | --- |
| 手机连拍（间隔 <1s）且 GPS 有效 | **每对相邻连拍会少一张**，且少的是后一张（序号大的） |
| 同一地点多次补拍（隔几秒） | 不受影响（>1s 容差） |
| GPS 缺失/被剥离 | 不受影响（走降级分支，本就要求派生后缀） |
| 合成素材全部用例 | 不受影响（事件内照片间隔 30s） |

**为什么之前所有测试都是绿的**：合成素材刻意让同事件照片间隔 30s（为了让它们落在 5min 归组窗口内且互不重复）。
这个设计让"连拍"这一最常见的真实场景**从未被覆盖**。

## 7. 与 P1-3（GPS 部分剥离）的关系

P1-3 记录的是"未授权时 GPS 剥离呈部分生效"，当时的结论是"去重判据不能假设 GPS 全有或全无"。
本次缺陷是它的**镜像**：GPS **全部有效**时反而更容易误删，因为有效 GPS 把照片推进了
「时间 + 距离」分支，而这个分支没有内容判据。

两件事合起来的结论更准确：
**去重不能依赖 GPS 作为"同一张"的证据，GPS 只能证明"同一地点"。**

## 8. 遗留与后续

1. **合成素材有结构性盲区**：无 <1s 连拍用例。建议在 `make_sample.py` 补一组"同地点 3 连拍（间隔 800ms）"，
   否则这条缺陷只能靠真实素材兜住。补素材会改变基线（照片数 66 → 68），需同轮重建两端基线。
2. **T11（去重重构）必须保留"锚点语义"**：不能因为"这是重构"就退回"时间 + GPS 两两判重"。
   本次修复的注释已写明取舍理由。
3. **台账只嵌前 2 张照片**（`照片1` / `照片2` 两列），而真实事件常有 5~7 张（本次 01 事件 7 张）。
   这是既有设计，不是缺陷，但真实使用中可能被质疑；已登记待产品确认。

## 9. 回滚

`git revert` 引入本次修复的提交即可。回滚后：
- 单元测试中新增的 regression 会失败（预期）；
- 真实素材会退回"110 张导出 54 张"，即重新开始丢照片。

因此**不建议单独回滚本次改动**；若必须回滚，需同时把去重设置改为"两者都保留"（KEEP_BOTH）以规避丢照片。
