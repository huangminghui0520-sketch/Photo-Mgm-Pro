## 3. 发现的问题（首轮实测）

### 观察 1：`_original` 未触发「派生合并」——这是正确行为（已核实）

首轮 dry-run 输出「派生合并 0 组」，但素材里有 55 组 `IMG_xxx.jpg` + `IMG_xxx_original.jpg` 双份。经核对代码，**这不是 bug**：

- `dedupDerived`（`algorithm/PhotoSource.kt:111`）只合并「**同基名 + 内容哈希一致**的复制副本」，不合并「内容不同的照片」。
- 水印相机的 `主图 IMG_xxx.jpg` 与 `_original` 原图是**内容哈希不同**的两张（`_original` 是去掉水印的合成版，或独立拍摄），按方案 B' 规则③（`PhotoSource.kt:171-173`），`_original` **正确保留为独立照片**。
- 所以「派生合并 0 组」=「这 55 组双份被正确识别为 110 张独立照片」，符合预期。

**真正的三态去重在 `groupDupContent`（时间+GPS 判重）**，它在**导出时**通过 `expandedEventMap` 生效：把「同一瞬间、同 GPS」的主图与 `_original` 判为一组，再按 `DedupKeepMode` 三选一（默认 `KEEP_WATERMARKED` 保留主图）。

**待验证（B 组导出时）**：这 55 组双份在导出时，`groupDupContent` 是否按「时间+GPS」正确归组，从而默认只导出主图、`_original` 不重复导出。这需要跑真实导出（去掉 `--dry-run`）后核对导出照片数。

### 观察 2：导出目录名过长被截断（真实边界问题，已决策并修复）

**根因澄清（2026-11-01）**：实测目录名末尾缺字，**并非 Windows 单段 255 字符上限所致**，而是 `ZipExporter.folderName` 里 `truncate(stripLeadingTime(description), 50)` 的 **50 字符硬截断**。那句日志原文 54 字符，截到 50 字符恰好停在「…做好记录，继」，缺「续巡查。」——与 Windows 无关。

**决策（已实现）**：目录名改为「序号_巡查日志内容」（去掉原「月日_」前缀），并**接受**部分长内容在末尾截断。截断规则统一收敛到 `ZipExporter.truncate`（`algorithm/ZipExporter.kt`）：
1. 换行/连续空白合并为单空格；
2. 描述超 50 字符 → 硬截断到前 50 字符（按字符数，中文/英文/数字各占 1）；
3. 末尾空白 trimEnd。
最终目录名长度 = 序号前缀(2) + `_`(1) + 描述(≤50) ≤ 53 字符，远低于 255 上限，不再触发系统级截断。月日信息已由台账「日期/结束时间」列完整保留。

- 影响：目录名完整且可预期；照片与台账不受影响（文件名独立）。
- 结论：已修复，见 `ZipExporterTest` 模板二系列用例。

### 问题 2：CLI 中文输出 GBK 乱码（低优先）

Windows 控制台默认 GBK，CLI 的中文输出（进度、事件清单、告警）直接乱码。加 `-Dfile.encoding=UTF-8` 可解决，但**最终用户双击运行的 GUI 不经过控制台**，所以这只影响 CLI 调试体验，不影响产品。

**待办**（低优先）：CLI 输出统一用 UTF-8 或检测控制台编码。

### 问题 3：`--dry-run` 仍强制要求 `--out`（已修复 ✅）

`--dry-run` 本意是「只分析不导出」，但 CLI 仍报「必须提供 --out」。属于参数校验的小 bug。

**修复（2026-11-01）**：`Runner.run` 里 `--dry-run` 时 `--out` 改为可选（不校验、不创建输出目录），
`outputDir` 置空。帮助文案同步标注「--dry-run 时可省略」。见 `desktop/cli/Main.kt`。

### C2/C3 实测结论（2026-11-01 补跑）

**C2 空格路径 —— ✅ 通过**。素材复制到 `...\ceshi 副本 含空格 测试`（源 + 输出均含空格）：
分析 110 张全读 / 33 条日志全解析 / 27 GPS 簇；真实导出 54 张（三态去重正确）、台账/清单/日志齐全、自检 ✔、0 失败。

**C3 长路径 —— ✅ 通过（含一处 JDK 层边界缺陷的兜底修复）**。源目录撑到 327 字符（> 260）：
- **发现**：JDK 17 在 Windows 下对超长路径，`java.nio.file.Paths.get` 会抛
  `InvalidPathException: Illegal character [?] in path at index 2`——`WindowsPathParser` 为访问超长路径
  主动加 `\\?\` 前缀、随后又把 `?` 判为非法字符（JDK 层缺陷，`java.io.File` 反而正常）。
- **修复**：CLI `Options.path()` 与 `--source` 目录校验对 `Paths.get` 做保护，超长路径给出
  明确提示「路径过长（超过 Windows 260 字符上限，请缩短目录层级）」，而非 `Illegal character [?]` 天书。
- **结论**：超长**源路径**不支持（属极罕见场景，Windows 资源管理器自身都难创建），但**不崩、有明确提示**，
  满足 C3 验证标准。`checkLongPaths`（导出目标 > 240 前置阻断）此前已覆盖导出侧，本修复补齐源侧提示。

### C7 实测结论（2026-11-01 补跑）

**构造**：用 `FileChannel.tryLock` 独占锁定一张源照片（模拟「照片被占用无法读取」），再运行真实导出。

**结果 —— ✅ 通过（有明确报错、不静默、无半成品残留）**：
- **明确报错**：`✘ 99_未分类/IMG_20261024_084736478.jpg —— 另一个程序已锁定文件的一部分，进程无法访问。`
  （Windows 原生可读错误，非天书）
- **不静默**：`照片目标 55 张：复制 54，跳过 0，失败 1` → 自检 `54/55 ✘` → `✘ 导出不完整（失败 1 条）`，退出码 `1`（EXIT_FAILED）。
- **计数自洽 + 无半成品**：失败照片被 `deleteIfExists` 清掉，`copied(54) + failed(1) == targets(55)`，
  下次续传不会把半个文件误判为完整产物。

> 附注：`attrib +R`（目录只读属性）**无法**阻止 Java 在目录内新建文件（Windows 目录只读位只影响目录自身的
> 删除/重命名，不阻止子项创建），故 C7 不用「只读目录」构造，改用「文件锁」构造才真正触发了写失败路径。

### C8 实测结论（2026-11-01 补跑）

**验证方式**：core 单测 `PcFolderExporterTest.取消导出后写入不完整清单且不命中续传`（`desktop/core/.../PcFolderExporterTest.kt:300`）
已覆盖取消语义，本次补跑确认绿。

> T10 之后该类改名为 `PcExportExecutorTest`（导出计划上移，执行器只负责写盘），**用例名与断言未变**；
> 本节是当轮（2026-11-01）的验证记录，不改写历史。

**结果 —— ✅ 通过**：
- 取消时 `isCancelled()` 钩子触发 → 停止复制、不写台账、`cancelled=true`；
- manifest 写入 `complete=false`，下次导出**不命中续传**（必须重导，避免把不完整产物当成品）；
- 计数不变式对取消场景豁免（`check(cancelled || copied+failed==targets)`），`skipped = targets - copied - failed` 自洽。

> 说明：CLI 为无头一次性运行，无交互式取消入口（`ProgressListener` 只 print 不调用 `handle.cancel()`）；
> 取消交互在 GUI（取消按钮 → core `cancel()`）体现。C8 的**核心语义**（取消后状态复位、无残留半成品）
