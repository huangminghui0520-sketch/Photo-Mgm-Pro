## 3. 发现的问题（首轮实测）

### 观察 1：`_original` 未触发「派生合并」——这是正确行为（已核实）

首轮 dry-run 输出「派生合并 0 组」，但素材里有 55 组 `IMG_xxx.jpg` + `IMG_xxx_original.jpg` 双份。经核对代码，**这不是 bug**：

- `dedupDerived`（`algorithm/PhotoSource.kt:111`）只合并「**同基名 + 内容哈希一致**的复制副本」，不合并「内容不同的照片」。
- 水印相机的 `主图 IMG_xxx.jpg` 与 `_original` 原图是**内容哈希不同**的两张（`_original` 是去掉水印的合成版，或独立拍摄），按方案 B' 规则③（`PhotoSource.kt:171-173`），`_original` **正确保留为独立照片**。
- 所以「派生合并 0 组」=「这 55 组双份被正确识别为 110 张独立照片」，符合预期。

**真正的三态去重在 `groupDupContent`（时间+GPS 判重）**，它在**导出时**通过 `expandedEventMap` 生效：把「同一瞬间、同 GPS」的主图与 `_original` 判为一组，再按 `DedupKeepMode` 三选一（默认 `KEEP_WATERMARKED` 保留主图）。

**待验证（B 组导出时）**：这 55 组双份在导出时，`groupDupContent` 是否按「时间+GPS」正确归组，从而默认只导出主图、`_original` 不重复导出。这需要跑真实导出（去掉 `--dry-run`）后核对导出照片数。

### 观察 2：导出目录名过长被截断（真实边界问题，已决策并修复）

**根因澄清（2026-11-01）**：实测目录名末尾缺字，**并非 Windows 单段 255 字符上限所致**，而是 `ZipExporter.folderName` 里 `truncate(stripLeadingTime(description), 50)` 的 **50 字符硬截断**。那句日志原文 54 字符，截到 50 字符恰好停在「…做好记录，继」，缺「续巡查。」——与 Windows 无关。

**决策（已实现）**：目录名改为「序号_巡查日志内容」（去掉原「月日_」前缀），并**接受**部分长内容在末尾截断。截断规则统一收敛到 `ZipExporter.truncate`（`algorithm/ZipExporter.kt`）：
1. 换行/连续空白合并为单空格；
2. 描述超 50 字符 → 硬截断到前 50 字符（按字符数，中文/英文/数字各占 1）；
3. 末尾空白 trimEnd。
最终目录名长度 = 序号前缀(2) + `_`(1) + 描述(≤50) ≤ 53 字符，远低于 255 上限，不再触发系统级截断。月日信息已由台账「日期/结束时间」列完整保留。

- 影响：目录名完整且可预期；照片与台账不受影响（文件名独立）。
- 结论：已修复，见 `ZipExporterTest` 模板二系列用例。

### 问题 2：CLI 中文输出 GBK 乱码（低优先）

Windows 控制台默认 GBK，CLI 的中文输出（进度、事件清单、告警）直接乱码。加 `-Dfile.encoding=UTF-8` 可解决，但**最终用户双击运行的 GUI 不经过控制台**，所以这只影响 CLI 调试体验，不影响产品。

**待办**（低优先）：CLI 输出统一用 UTF-8 或检测控制台编码。

### 问题 3：`--dry-run` 仍强制要求 `--out`

`--dry-run` 本意是「只分析不导出」，但 CLI 仍报「必须提供 --out」。属于参数校验的小 bug。

**待办**（低优先）：`--dry-run` 时 `--out` 应可选。
